# STracer Android: automatic upload-token enrollment and renewal

Updated 30 October 2026. This is the recommended setup for new app installations. Backend code and migration 007 must be deployed before app acceptance testing. Existing portal login, manual upload credentials, S3/PDF processing and company email delivery remain supported.

## Expected user experience

The user continues entering a mobile number and company code. The app registers its installation automatically, shows a pending approval message, and obtains its own upload token after the administrator recognizes/approves the device. Later token renewals happen automatically. Users and developers do not exchange upload tokens manually. No portal email/password or OTP is added to the mobile login screen.

**First-time device approval is still required.** Mobile number, company code and user ID identify a record; they do not prove possession of that account. This implementation does not automatically approve a device based solely on those fields. The administrator must verify the physical installation and its displayed verification code before approval.

Flow: app creates installation secret → pending enrollment → trusted administrator approval → automatic token retrieval → ZIP upload → automatic renewal → PDF and email processing.

## 1. Deployment and responsibilities

Deploy the updated backend and apply `007_rf_mobile_enrollments.sql` to **both IN and TW databases**, after migration 006. The existing `--rf-log-db-migrate` and `--rf-log-db-check` commands include the new table. Use `scripts/Deploy-RfLogIntegration.ps1` with the extracted release, preserving live `web.config`, S3, SMTP and regional settings. Do not add `-ConfigureStorage` for a normal update.

The backend operator reviews new devices, without copying tokens. The Android developer implements the registration, polling, secure secret/token storage and renewal calls below. The registered user must already be active and linked to a valid company in the correct region; enrollment does not create users, activate accounts or repair incorrect company assignments.

## 2. Installation identity created by the Android app

Before the first registration request, generate and securely persist:

| Item | Generation / use |
| --- | --- |
| `enrollmentId` | Random UUID, stable for this installation and registered account. |
| Enrollment secret | 32 cryptographically random bytes encoded as exactly 64 lowercase hex characters. Generate locally with a cryptographically secure random generator. |
| User association | Existing `userId`, mobile number, company code and explicit `IN` or `TW` region. |
| Device label | A recognizable description such as the assigned test-phone name. A label is not hardware attestation. |

Store the enrollment secret and tokens in Android Keystore-backed encrypted storage; exclude them from logs, backups, screenshots, analytics and crash reports. Keep them associated with the correct user/company/region. Switching accounts or reinstalling without the secret requires a new enrollment and approval. Never distribute one common installation secret in the APK.

The enrollment secret is a long-lived proof used only by the enrollment/token endpoints. It is different from the short-lived upload bearer token. Never send the secret in a URL/query parameter or to storage/third-party origins. Use the configured HTTPS backend origin and do not forward authorization headers across redirects.

## 3. Request enrollment automatically

```http
POST https://s-traccceer.vinfocom.co.in/api/rf-logs/mobile-enrollments
Content-Type: application/json
X-RF-Enrollment-Secret: <64 lowercase hex characters generated by the app>
```

```json
{
  "enrollmentId": "<persisted UUID>",
  "region": "IN",
  "userId": 338,
  "mobileNumber": "<registered mobile number>",
  "companyCode": "<registered company code>",
  "deviceLabel": "<installation label>"
}
```

The example user ID is illustrative; use the logged-in mobile record's real ID. A valid request returns `202` with `status: "pending"`, `enrollmentId`, `deviceVerificationCode`, expiry information and `pollAfterSeconds: 30`. It returns **no upload token**. Preserve the ID, secret and exact registration payload across retries. A repeated identical request returns the existing enrollment. Another secret cannot take over the same ID.

Pending requests expire after 48 hours. At most five unexpired pending requests are allowed per user/region; reuse existing requests rather than creating a new UUID on every retry. The public endpoints also use the existing IP-based `PublicApi` rate limiter. Registration does not grant access to a drive session or send email.

## 4. One-time administrator approval

Display `deviceVerificationCode` in the app while waiting. The administrator must confirm this matches the intended installation through a trusted process. Do not approve unknown requests only because their phone number/company code looks familiar.

The existing logged-in company administrator can list/review requests using:

```http
GET /api/rf-logs/mobile-enrollment-requests
POST /api/rf-logs/mobile-enrollment-requests/{enrollmentId}/decision
Content-Type: application/json
X-CSRF-TOKEN: <matching st.csrf cookie>
```

```json
{"decision":"approve"}
```

Use `deny` to reject a pending request or disable an approved device. These APIs require the existing administrator cookie and are restricted to that administrator's company/region. Mobile bearers and enrollment secrets cannot approve requests. Responses expose only safe metadata, not the enrollment secret, full proof hash or token.

Alternatively, the Windows backend operator can approve locally from **Administrator PowerShell**, without portal email/password:

```powershell
.\scripts\Review-RfMobileEnrollment.ps1 -EnrollmentId '<ID shown in the app>' -Region IN
```

Use `-Decision deny` to reject/disable. Set `-BackendPath` if the deployed API is not in `C:\inetpub\wwwroot\Backend`. This script runs the new server-local `--rf-mobile-enrollment-review` command using the site's existing database configuration. The updated script alone will not add this command to old binaries. No upload token is printed or shared by the approval operation.

Approval is valid for up to 365 days and cannot revive a denied, revoked or expired installation. At the end of that period, create a fresh enrollment for trusted review. Manual token issuance remains an optional compatibility path, not a required part of this automatic flow.

## 5. Poll status without portal login

```http
GET https://s-traccceer.vinfocom.co.in/api/rf-logs/mobile-enrollments/{enrollmentId}?region=IN
X-RF-Enrollment-Secret: <persisted enrollment secret>
```

Respect `pollAfterSeconds` (30 seconds) and use platform-appropriate background scheduling/backoff. Stop polling when the request is denied, expired or inactive. Keep the same ID/secret. The app may observe `pending`, `approved`, `denied`, `expired` or `inactive`; an incorrect secret or region cannot inspect the enrollment.

## 6. Retrieve and renew the upload token automatically

Once approved, generate and persist a random `renewalId` UUID **before** requesting a token:

```http
POST https://s-traccceer.vinfocom.co.in/api/rf-logs/mobile-enrollments/{enrollmentId}/token
Content-Type: application/json
X-RF-Enrollment-Secret: <persisted enrollment secret>
```

```json
{"region":"IN","renewalId":"<persisted renewal UUID>","previousRenewalId":null}
```

The `200` response contains:

| Field | Meaning |
| --- | --- |
| `tokenType` | `Bearer`. |
| `uploadToken` | The access credential to attach to RF upload/status/download calls. |
| `credential.credentialId` | Stable installation credential ID, allowing renewed tokens to access existing uploads. |
| `credential.expiresAtUtc` | Access-token expiry, normally 30 days, capped by approval expiry. |
| `approvalExpiresAtUtc` | Absolute device-approval expiry. |
| `renewBeforeSeconds` | Suggested renewal lead time: 86400 seconds (24 hours). |
| `renewalId` | Successful renewal ID; save it for the next rotation's `previousRenewalId`. |

Persist the response securely. For the first token request, use `previousRenewalId: null`. For a lost network response, retry using the **same latest renewal ID and payload**; the server returns the same token and expiry. For the next scheduled renewal, generate/persist a new renewal ID and set `previousRenewalId` to the last successful renewal ID. Serialize these requests across app/background workers. The server uses an atomic comparison so only one competing new renewal can win; a stale competing request returns `409` instead of replacing a newer token. Recover the current `latestRenewalId` through proof-authenticated status polling and POST that same ID to retrieve the winning token. Once a newer renewal succeeds, older bearer tokens are invalid; use the newly stored token for subsequent uploads.

Renewal works after access-token expiry if device approval and the enrollment secret are still valid. A revoked credential cannot be revived by renewal. A disabled/reassigned user or company, changed registered mobile/company code, denied enrollment or expired approval blocks renewal. Near absolute approval expiry, do not repeatedly renew expecting an extension; arrange a new trusted enrollment.

The server stores proof/token hashes, not raw secrets or bearer tokens. Retry recovery uses the installation proof and renewal ID; a database record alone cannot recover them.

## 7. Upload the final drive ZIP

After drive completion, finish writing the ZIP and call:

```http
POST https://s-traccceer.vinfocom.co.in/api/rf-logs/upload
Authorization: Bearer <current uploadToken>
```

Send multipart fields `file`, a stable per-ZIP `uploadId`, and the existing `sessionId`. Optional `projectId` must be a positive ID in the same company; omit it if unavailable, never send `0`. Omit `subSessionId` if unavailable. `userId`, company scope and region are derived from the approved credential; do not override them to upload another user's session.

Use a native HTTP client without portal cookies. Enrollment and bearer-only upload do not require portal email/password, OTP or a CSRF header. Existing browser/portal cookie requests remain subject to their existing CSRF rules. Let the client generate the multipart Content-Type/boundary. Do not attach the enrollment secret to ZIP uploads.

Retain the same ZIP bytes, metadata and upload UUID across retries. Renewal preserves the installation credential ID, so retries/status checks keep the same upload ownership. A new enrollment/reinstall is a different credential and does not automatically inherit another installation's uploads.

The backend verifies ownership, saves the ZIP privately, generates the PDF and queues email to the company's registered `tbl_company.email` plus eligible additional recipients. `200` means upload acceptance, not completed PDF generation or inbox delivery. No additional Generate PDF/Send Email action is required. Supported NetworkLog data and available map screenshots must be in the ZIP; authentication does not create missing screenshots or measurements.

## 8. Client error handling

| HTTP result | Required action |
| --- | --- |
| `202 pending` | Wait for trusted device approval; no token is available yet. |
| `400` | Correct request fields, region, UUIDs or secret format. |
| `401` on upload | Attempt one serialized token renewal, then retry once with the same upload UUID. |
| `401` on token endpoint | Credential revoked/mismatched, or the last renewal has expired. For an expired renewal, use a new renewal ID; a revoked device needs a new approved enrollment. Do not loop. |
| `403` | Approval/ownership/account restrictions. Inspect enrollment status and correct the user/company/session or request trusted approval. |
| `404` enrollment | Incorrect ID/region/secret or unavailable record. Do not fall back to unauthenticated upload. |
| `409` | Registration conflict, ID collision, denied/expired approval, or conflicting upload metadata. Preserve saved identities and investigate before creating replacements. |
| `429` | Back off; avoid repeated registrations and respect the pending-device limit. |
| `503` | Server configuration/database/storage issue. Preserve local ZIP/enrollment state and retry transient failures with backoff. |

## 9. Acceptance checklist

- Pending devices cannot obtain tokens, upload data or approve themselves.
- Administrator approval is company/region scoped, CSRF-protected for browser callers, and performed only for the recognized device/code.
- The approved app receives its token directly; no token is copied to users or developers.
- Lost token-response retries recover the same latest token/expiry.
- Automatic renewal invalidates the previous bearer while preserving access to that installation's prior uploads.
- Credential revocation, denied enrollment, inactive/reassigned users and expiry prevent further access/renewal.
- The existing portal email/password login, cookie/CSRF behavior, manual credentials and RF report/email pipeline still pass regression tests.
- A real Android enrollment, approval, ZIP upload, PDF and inbox-delivery test is required after production deployment; local tests alone do not establish production acceptance.
